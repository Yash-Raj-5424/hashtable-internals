- we use hash functions to map application keys to integer in order to store them in the array
- and since collisions are inevitable, re-calculating the hash-key for every appli-key would be expensive
- so we store both the `key` (a generic type) and `hash_key` in a custom key type
- now that we're storing generic type key, we'll need to compare two such keys. how do we do this ? => we would need a custom comparator for the type so that our implementation becomes generic enough
- we also need a destructor-fucntion for cleaning-up the references of the deleted keys [in case the lang has manual memory magmt]

**hashset using chained hashtables**

- so hashset will have (array, array_size, key_count, comparator-function, destructor-fucntion)
- this is how the LL node of the hashtable would look when we're implementing a hashset:
```
struct node{
    int32 hash_key; // hash of key to avoid re-computation
    void * key; // application key
    struct node * next;
}
```

- to have fast inserts, we'll prepend the keys at the head of the list (in case of collisions on a key)
- to have just unique keys in the array, we'll check everytime before the insert (this'll make the inserts expensive)

**hashset using open addressing hashtable**
- hashset will have (array, key_count, used_slot_count, comparator-func, destructor-func)
- this is how a slot in the array would look in this case:

```
struct slot{
    bool is_empty;
    bool is_deleted;
    int32 hash_key;
    void * key;
}
```

- during the lookups/insert/delete we explicitly compare the keys when we find matching keys to check its existence => this is where comparator-func is used
- the destructor should only be invoked on hard-deletes
